# 渲染反馈闭环（Render Feedback Loop）

> 何时读我:页面已经写完但还没交付时;或交付过一次却在真实浏览器里"跟设计对不上"时。
> 最短路径:渲染→qc 对账→修→evidence→五镜。
> 回 INDEX:SKILL.md「参考文档(30 秒路由)」。

静态审计(lint/audit)看不见渲染时才暴露的问题:变量被覆盖、样式没加载、构建管线吞色。
每一样都让"声明"与"实况"脱节——而用户只看实况。闭环的意义:**用渲染事实关闭声明与实况的缝**。

## 闭环五步(每页必走)

1. **渲染**:宿主有浏览器工具就整页截图(视口分段,勿全页拼接——长页平铺伪影教训);
   没有浏览器工具则明确声明"未过渲染闸",不得谎称已验。
2. **qc 对账**:`qc shot.png --tokens tokens.json`(或 --palette+--bg)——大底真伪、
   板外入侵、面积份额,一条命令出指纹绑定 JSON。大底漂移是双哈希类 bug 的铁指纹。
3. **修**:qc 的每条 finding 带修复方向;修完重渲染重跑,直到 PASS。
4. **交付门**:`evidence page --palette`(四闸+静态审计)作为交付记录,与 qc 的图像
   指纹互相印证(页面字节、渲染像素、声明色板三方对账)。
5. **五镜**:构图/密度/视线顺序/删减/签名是视觉判断,机械闸不覆盖——截图人审(五镜)
   仍是最后一道;五镜发现的问题回改后重走 1-4。

## 规则:声明即契约

页面里出现的每一个颜色都应能追溯到声明(tokens.css/主题包/色板)。
qc 报出的每一个板外色,要么修掉,要么"补进声明"——没有第三种状态。
"它看起来差不多"不是对账通过;ΔE 数字通过才是通过。

## 验收清单(交付前逐项)

- [ ] 渲染截图 ≥1 张(视口真渲染,非代码想象)
- [ ] qc 裁决 PASS(bg 对账+板外清零),指纹入交付记录
- [ ] evidence 裁决 PASS(四闸+lint)
- [ ] 五镜自审完成,发现项已回改并重过 1-4
- [ ] 三方可对账:页面源码色 ↔ tokens 声明 ↔ 渲染像素
